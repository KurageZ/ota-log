# 活动数据结构设计

本文档用于沉淀 ota-log 活动与相关数据结构的长期设计讨论。当前已实现 schema 仍以 `src/db/schema.ts`、`src/db/migrations.ts` 和 Migration v15 为准；本文档记录下一阶段设计目标、取舍和待决策问题。

## 当前模型摘要

当前活动模型以用户本地记录为中心：

- `events` 保存活动标题、日期、时间、城市、场地、状态、票价、备注、详情、链接和 setlist。
- `event_artists` 保存活动与艺人的多对多关系。
- `expenses` 可挂在活动上，前台主要维护活动级花费。
- `photos`、`cheki`、`cheki_manual_entries` 可与活动关联。

这个模型适合个人记录，但对复杂公开活动事实支持有限，例如多场次、票种、结构化地点、官方时间表、外部来源 ID、父子活动等。

## 长期设计目标

- 区分公开活动事实和用户个人记录。
- 保留用户手动覆盖能力，避免云端或外部来源更新覆盖用户整理过的字段。
- 对 ievent.life 等结构化来源保持较高保真，不把关键结构压平成 `details` 文本。
- 让活动、场次、地点、票种、时间表、出演者关系有清晰边界。
- 迁移必须保护本地旧数据，并给出测试覆盖。

## 待决策问题

- 是否引入 canonical activity metadata 与 user activity record 的双层模型。
- 字段覆盖规则采用字段级 override、整条记录 fork，还是混合策略。
- 父子活动、分场次、时间表在 UI 上如何呈现，避免增加普通记录成本。
- ticket types 与用户实际花费如何区分。
- 外部来源数据是作为 sidecar 保存，还是进入主活动模型。

## 迁移约束

- 数据库变更必须通过 `PRAGMA user_version` 管理。
- 普通新增字段优先使用增量 `ALTER TABLE`。
- 修改约束或列定义时可采用表重建模式，但必须保留旧数据并补测试。
- 数据库相关测试放在 `src/db/__tests__/`，至少覆盖结构变化、旧数据保留和 Repository 读取。

## 更新触发

- 修改 `events`、`event_artists`、`expenses`、`photos`、`cheki` 或相关 Repository。
- 增加外部活动导入能力。
- 重新定义活动、场次、地点、票种、时间表、出演者的边界。
- 发现现有模型无法无损表达真实来源数据。
