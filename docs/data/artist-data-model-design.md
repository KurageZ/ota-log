# 艺人类型与所属关系数据模型

本文档描述 Migration v22 起的艺人类型、普通所属和正式团体履历。核心目标是在不强迫所有旧记录分类的前提下，让“个人因团体出演而参加活动”的统计受在团时间约束。

## 核心原则

- `artists.artist_type` 可为 `person`、`group` 或 `NULL`；`NULL` 表示用户尚未设置，不是第三种艺人类型。
- 新建和从旧版本升级的艺人默认保持未设置。
- 未设置类型仍可直接关联活动、拍立得、重要日期、收藏和单推，但不参与任何所属关系的间接查询或自动归因。
- 未设置类型之间可以保留一对多、可嵌套且无日期的普通所属；普通所属不允许自关联或回路。
- 只有个人可以加入团体。团体不能加入团体；多级组织未来通过独立文件夹能力解决。
- 一位个人可以同时加入多个团体，也可以在同一团体保存多段不重叠的履历。

## 表结构

### `artists`

`artist_type TEXT NULL CHECK (artist_type IN ('person', 'group'))` 保存显式类型。旧 `parent_id` 列在 v22 被移除。

### `artist_basic_affiliations`

保存未设置类型记录之间的普通所属：

- `member_artist_id` 是主键，因此每个成员最多有一个直接所属。
- `parent_artist_id` 可以拥有多个直接成员。
- 两端必须都保持未设置类型。
- 删除任一艺人时级联删除关系；不会删除活动、拍立得或本地图片文件。

### `artist_group_memberships`

保存个人加入团体的正式履历：

- `start_date`、`end_date` 均可为空，精度为日，两端包含。
- 空开始日期表示更早时间未知，空结束日期表示仍在团或结束时间未知。
- 同一人和同一团体可以保存多段履历，但日期范围不能重叠；首尾相邻允许。
- 不同团体之间可以重叠，表示兼任。
- 数据库触发器验证个人/团体类型、日期顺序和区间重叠。

“当前所属”以今天落在闭区间内判断。未来开始的履历不在当前摘要中展示，但活动仍按实际日期正确命中。

## 活动归因

`event_artist_attributions` 视图提供统一口径：

1. 活动直接关联某艺人时始终归因给该艺人。
2. 活动直接关联团体时，任一场次的日期范围与个人的正式所属区间相交，即归因给该个人。
3. 多场次、跨午夜和多条命中最终按“活动 + 艺人”去重。
4. 普通所属、团体反向继承和团体套团体均不参与归因。

活动级阵容无法表达某位成员只参加其中一个具体场次；当前采用“任一场次命中则整场活动归因”的口径。需要更精确时应新增场次级出演关系，而不是猜测。

## 拍立得口径

拍立得只属于 Record 直接关联的艺人，不沿普通所属或正式团体履历连续查询，也不从团体归因给个人。

## 迁移与备份

- v22 升级：所有旧艺人保持未设置，旧 `parent_id` 转为普通所属；不强制进入迁移确认页。
- 设置 → 数据与备份提供批量类型转换。未设置类型且已有所属关系的艺人只能整组转换：组内成员转为个人、上级转为团体；孤立艺人单独选择类型，默认设为个人并允许用户改为团体，「单独艺人」分区提供「全选为个人 / 全选为团体」批量设置。普通所属以完整关系组联动勾选或取消，「已有所属关系」分区提供全选。转换页按 `event_artists` 的直接活动数量优先展示有活动的关系和艺人。用户逐项检查并最终确认后，被选中的普通所属转换为无日期正式履历。被触及的普通所属必须整体形成“个人 → 团体”，否则拒绝转换。
- 完整备份 v9 保存类型、普通所属和正式履历。
- 恢复 v1–v8 备份时不推断类型；旧 `parent_id` 恢复为普通所属。
- Chekiroku 本轮仍导入为未设置类型与普通所属。后续适配时，源团体应明确为团体、源成员应明确为个人，并生成无日期正式履历。
