# iOS 实时活动（Live Activity）设计

> 状态：已实现，待真机视觉验收。
>
> 范围：仅 iOS、本地优先、单实例，不需要服务端。
>
> 技术基线：Expo SDK 57、`expo-widgets`、`@expo/ui/swift-ui`；项目最低部署版本为 iOS 17.0。

## 1. 产品定位

实时活动是活动详情页在系统界面中的临时延伸。用户已经到场或即将到场时，可以不解锁手机就看到当前活动、当前时间表条目、下一条目和剩余时间。

它不是完整时间表、通知中心或后台调度器。活动详情与本地 SQLite 始终是事实来源；实时活动只展示最近一次由 App 计算并提交的状态。

### 目标

- 在锁屏、灵动岛及系统派生形态中快速回答「现在是什么、还剩多久、下一项是什么」。
- 有结构化时间表时优先展示当前条目和下一条目；没有时间表时回退为场次级展示。
- 用户打开相关活动详情后自动启动，不要求额外配置服务端、APNs 或账户。
- 点击任一形态直接进入对应活动详情。
- 对纯本地方案的更新限制保持诚实，不把旧条目伪装成实时数据。

### 非目标

- 不做 Android 版；常驻通知、前台服务和 Android Live Updates 另行设计。
- 不做服务端推送、push-to-start、推送 token 或 APNs 通道。
- 不扫描数据库后在后台自动发现活动；用户从未打开相关活动详情时不启动。
- 不在实时活动中展示完整时间表、海报、备注、支出、票务或私人记录。
- 不支持多个活动同时显示；首版全局只保留一个 ota_log 实时活动。

## 2. 数据事实与时间口径

数据来自现有结构：

- `Event`：活动标题、状态和活动详情深链目标。
- `EventSession`：场次标题、日期、开场、开演、结束日期与结束时间。
- `EventTimetableEntry`：条目标题、开始时间、结束时间与稳定的 `sort_order`。

所有日期和时间按设备当前本地时区解释。数据模型暂不保存 IANA 时区，因此跨时区提前查看的精确换算不属于首版范围。

### 2.1 有效场次窗口

场次必须能形成有界窗口才可启动实时活动：

1. 实时活动的首个边界优先取 `session.open_time`，未填写时取 `session.start_time`。从首个边界前 30 分钟进入可显示窗口。
2. 有效结束时间优先取场次的 `end_date ?? session_date` + `end_time`。
3. 场次未填写 `end_time` 时，优先回退到时间表中最晚的显式 `end_time`；不能用最后一条的开始时间推断整个场次结束。
4. 仍无法得到结束时间时，默认以开演时间后 4 小时作为结束边界；未填写开演时间时以开场时间为准，且不得跨过开始日期的午夜。此时演出开始后显示经过时间，而不是距离推定结束时间的倒计时。
5. 未填写 `end_date` 且结束时刻早于开始时刻时，不自动假定跨天；需要用户补充结束日期。

只有状态为 `planned` 的活动参与自动启动。`wishlist`、`cancelled` 和已经完成的活动不启动。

### 2.2 时间表条目窗口

只有填写 `start_time` 的条目参与当前/下一条目计算；无开始时间的条目仍保留在 App 时间表中，但不进入实时活动。

条目的有效结束时间依次取：

1. 条目自己的 `end_time`；
2. 同一场次中下一条有开始时间的条目的 `start_time`；
3. 场次有效结束时间。

如果三者都不存在，该条目只显示「进行中」，不展示虚构的倒计时。条目按有效开始时间、再按 `sort_order` 稳定排序；窗口重叠时，取开始时间更晚的条目为当前条目，仍相同时取 `sort_order` 更大的条目。下一条目取当前时刻之后开始时间最早的一条。

跨午夜场次使用 `end_date` 生成绝对时间；跨日时间表条目继承场次日期，早于场次开始时刻的条目时间只有在场次明确跨天时才解释为次日。

## 3. 生命周期

### 3.1 启动条件

用户打开某个活动详情，且存在一个同时满足以下条件的场次时，自动启动：

- 活动状态为 `planned`；
- 当前时间位于「开场前 30 分钟」至有效结束时间之间；未填写开场时间时，从开演前 30 分钟开始；
- 场次有有效开始时间；结束时间缺失时按上述 4 小时且不跨日的规则推定；
- 用户没有在本场次中关闭或移除过实时活动。

如果页面在前台停留并进入上述 30 分钟窗口，也应启动。提前超过 30 分钟打开后离开页面，不在后台定时启动。

同一活动有多个场次同时命中时，优先选择已经开始且开始时间最晚的场次；若都未开始，选择最早开始的场次；仍相同时按 `sort_order`。打开另一场符合条件的活动时，先以 `immediate` 结束旧实例，再启动新实例。

### 3.2 展示状态

#### 即将开场

- 时间：同时填写开场和开演时间时，从开场前 30 分钟至开场时刻；只填写开场时间时，从开场前 30 分钟至开场时刻。
- 主信息：活动标题；有场次标题时同时展示。
- 计时：原生倒计时「距开场」。
- 辅助信息：场馆；无场馆时不占位。

#### 即将开演

- 时间：开场时刻至开演时刻；只填写开演时间时，从开演前 30 分钟至开演时刻。
- 主信息：活动标题；有场次标题时同时展示。
- 计时：原生倒计时「距开演」。
- 辅助信息：场馆；无场馆时不占位。

#### 进行中——有时间表

- 主信息：活动标题与「正在进行中」。
- 时间表信息：命中当前条目时显示当前条目头像和标题；存在下一条目时，以箭头连接下一项头像，缺少图片时显示标题首字符头像。
- 有时间表时不显示倒计时，也不显示「更新于」。

当前时刻没有命中任何条目，但未来仍有已定时条目时，当前条目区域为空，仅显示箭头和下一项头像；最后一条结束后至场次结束前只保留活动/场次级展示。

#### 进行中——无可用时间表

- 主信息：活动标题与可选场次标题。
- 计时：显示距场次有效结束时间的倒计时。
- 不展示空的「当前」或「下一项」占位。

#### 已结束

- App 仍存活或下次回到前台时，立即调用 `end`，最终状态显示「已结束」，并在 15 分钟后从锁屏移除。
- 灵动岛在结束时由系统立即移除。
- 活动取消、删除、改期到窗口外或被另一活动替换时不保留总结，使用 `immediate`。
- App 被系统终止后无法在结束时刻主动调用本地 API；倒计时会停在零，标题也可能停留在旧条目，直到用户打开 App、手动移除，或系统达到生命周期上限。这是纯本地首版的已知限制。

### 3.3 更新与恢复

以下时机重新从 SQLite 计算并调用 `update`：

- 活动详情保持前台时跨越场次开始、条目开始或条目结束边界；
- App 从后台回到前台；
- 当前活动、场次或时间表在 App 内被编辑；
- 相关活动状态发生变化。

App 启动或回到前台时：

1. 使用 `getInstances()` 获取仍存活的实例；
2. 读取持久化的活动/场次标记，并与 SQLite 重新核对；
3. 已取消、已删除、已结束或已移出窗口的实例立即结束；
4. 仍有效的实例更新为当前状态；
5. 异常存在多个实例时，仅保留标记对应的一个，其余立即结束。

`expo-widgets` 的 Live Activity API 没有 Widget timeline 等价物。App 进程不运行时，SwiftUI `.timer` 文本仍可由系统推进，但 props、条目标题和生命周期不会由 ota_log 本地代码定时更新。

### 3.4 用户移除与重新开启

App 持久化一份轻量标记：`eventId`、`sessionId`、`startedAt`、`effectiveEndAt`。它不复制业务内容。

- 若标记仍在有效期内但 `getInstances()` 已无实例，视为用户或系统已经移除，本场次不再自动重启。
- App 内主动关闭时立即结束并隐藏活动详情中的实时活动入口，同时保留关闭状态至本场次结束，避免再次打开页面就自动重启。
- 正常结束、活动删除或场次越过有效结束时间后清除标记。

### 3.5 八小时上限

单个 Live Activity 最多保持活跃约 8 小时。场次超过 8 小时时：

- 不拆分或预排多个实例；
- 当前实例由系统在上限处结束；
- 达到上限后不在活动详情展示过期状态或重新开启入口；
- 不承诺两个实例之间无缝衔接。

## 4. 活动详情入口

实时活动入口属于当前场次的运行状态，不新增全局设置页。活动详情仅在 iOS 且该活动的 Live Activity 正在系统中显示时，显示一行「实时活动」状态：

| 状态 | 副文案 | 操作 |
|---|---|---|
| 已自动启动 | 正在锁屏与灵动岛显示 | 关闭 |
| 已手动关闭 | 已关闭 | 开启 |

尚未进入窗口、缺少时间、不可用、已过期、已结束以及非当前活动均不渲染该行，也不保留空白占位。入口复用详情页现有卡片、分隔线和 `AppIcon` 业务图标，不新建高饱和 Hero，不把运行状态只交给颜色表达。首次自动启动不弹成功对话框；关闭后该行立即切换为「已关闭 / 开启」，点击「开启」会强制重建当前场次的 Live Activity。关闭和重新开启均提供轻触觉反馈。

## 5. 系统界面设计

整体使用系统提供的 Live Activity 材质背景和低面积 accent 点缀。锁屏根视图不传递 `activityBackgroundTint`，避免 Expo widget runtime 在原生 modifier 解析失败时把整个 `banner` 静默降级为 `EmptyView`。锁屏壁纸、Always-On 与深色模式不可控，因此不使用整块品牌渐变或低对比度装饰。活动资料图在锁屏与 expanded 中显示第一张，进入 props 前缩放并转为小尺寸 JPEG 后复制到 `widgetsDirectory`，避免扩展进程解码高分辨率原图失败。

### 5.1 锁屏横幅 `banner`

锁屏与 expanded 使用一致的信息层级，采用左图右文的横向结构，整体高度控制在 160pt 内：

1. 左侧显示活动资料图，固定比例裁切并使用连续圆角；没有图片时文字区自然扩展，不保留空白占位。
2. 右侧依次显示大号演出标题与「即将开场」「即将开演」「正在进行中」或「已结束」。
3. 开场前显示「场馆 · 开演 HH:MM」，缺少其中一项时只显示可用信息，不预告时间表条目。
4. 进行中无时间表时显示语义标签与系统动态计时；有时间表且命中当前条目时显示当前条目头像和标题，当前项不显示时间，并以箭头连接下一项头像与开始时间。
5. 时间表出现空档时不冒充当前条目，仅显示箭头和下一项头像；下一项缺少图片时使用标题首字符头像。
6. 场次标题与演出标题不同时放在文字区底部。锁屏不显示「更新于」或旧版的下一项文字行。

锁屏根布局使用左右 20pt、上下 16pt 的内容留白，并避免传递无法安全跨 JSON 桥接的非有限 frame 数值。信息不足时直接缩短高度，不保留空白占位。点击整卡通过 `otalog:///events/{eventId}` 打开活动详情。

### 5.2 灵动岛

- `compactLeading`：演出进行中且命中当前时间表条目、条目艺人有可用本地头像时，显示 22pt 圆形艺人头像；开场前、时间表空档、无头像或无时间表时显示 22pt 圆形 App Icon。图片均保留原色，不增加朝向原深感摄像头一侧的额外 padding。
- `compactTrailing`：不重复锁屏与 expanded 的倒计时，只显示当前阶段：「开场前」「开演前」「进行中」「待下一项」「演出中」或「已结束」。文字使用固有宽度，不设置 frame 或额外 padding，使内容贴近原深感摄像头并避免无意义地撑宽。
- `minimal`：复用 `compactLeading` 当前选择的艺人头像或 App Icon，不显示倒计时或标题，避免把最小形态横向撑长。提供完整 accessibility label。
- `expandedLeading`：留空，不显示阶段图标，避免挤压中央内容区。
- `expandedTrailing`：留空；expanded 的关键信息统一进入中央阅读顺序，避免再次压缩文字宽度。
- `expandedCenter`：在同一个横向容器中显示活动资料图和文字，统一按「大号演出标题 → 状态 → 第三层信息」排列。开场前第三层显示「场馆 · 开演 HH:MM」，缺少其中一项时只显示可用信息，不预告时间表条目；进行中无时间表时第三层为距结束计时，默认结束边界下显示「已开始」经过时间；进行中有时间表时第三层显示当前条目头像与标题，当前项不附带时间，下一项通过箭头连接并显示头像与开始时间。当前没有命中条目时不占位。图片与文字共同使用明确的展开态内容宽度。
- `expandedBottom`：仅在场次标题与演出标题不同且有区分价值时显示场次标题。不显示场馆、下一项或「更新于」。

动态岛背景由系统控制，设计不依赖自定义背景色。暂不单独提供 `bannerSmall`；CarPlay、watchOS 及系统小尺寸派生形态按 `expo-widgets` 的回退规则复用 `banner`，避免 iOS 根据 `activityFamily` 进入另一套未经验证的锁屏渲染路径。

### 5.3 排版与状态适配

- 标题优先保证当前条目可读；活动名、场次名和下一项按上述层级依次截断。
- 倒计时使用 `@expo/ui/swift-ui` 的原生 timer 能力与等宽数字，不用 JS 每秒刷新。
- `environment.colorScheme` 选择浅色或深色 accent，主次文本使用 SwiftUI 系统层级颜色；`isLuminanceReduced` 时减少 accent 强度，不依赖动画。
- `isActivityUpdateReduced` 或 `levelOfDetail === 'simplified'` 时仍优先保证标题、阶段与关键当前信息可读。
- 所有形态提供组合后的中文 accessibility label，例如「进行中，星空舞台，距离结束 12 分钟，下一项 20 点 10 分」。
- 文本不使用跑马灯；标题最多两行，紧凑形态只保留一个信息焦点。

## 6. Props 与实现边界

Live Activity props 只携带渲染所需快照，不在 widget runtime 查询数据库：

```ts
interface EventLiveActivityProps {
  phase: 'upcoming' | 'running' | 'ended';
  eventTitle: string;
  sessionTitle?: string;
  upcomingDetails?: string;
  primaryTitle: string;
  currentEntryTitle?: string;
  nextEntryTitle?: string;
  nextEntryInitial?: string;
  nextEntryTime?: string;
  hasTimetable: boolean;
  nextLabel?: string;
  currentArtistAvatarUri?: string;
  nextArtistAvatarUri?: string;
  eventImageUri?: string;
  appIconUri?: string;
  countdownTargetAt?: number;
  countdownKind: 'opens' | 'starts' | 'ends';
  timerStartAt?: number;
  timerMode: 'countdown' | 'elapsed';
  updatedAt: number;
  lightBackground: string;
  darkBackground: string;
  lightAccent: string;
  darkAccent: string;
}
```

实现约束：

- `createLiveActivity` 名称只需与代码中的 factory 一致；不要把 Live Activity 误加到 `app.json` 的 `widgets[]`。
- widget 组件使用 `'widget'` 指令，保持纯函数；所有动态内容通过 props 和 `LiveActivityEnvironment` 进入。
- 只使用 `@expo/ui/swift-ui` 组件和 modifiers，不引用 React Native 组件、Hook、Context 或模块级运行时状态。
- `getInstances()` 返回实例但业务身份依赖 App 自己的单实例标记；协调器必须以 SQLite 为最终事实来源。
- 不开启 `enablePushNotifications`，继续沿用项目的无推送 widget 配置。
- ActivityKit 对 attributes 与 content state 合计有 4 KB 上限。实现只传预生成的短展示字段，对用户文本截断，并在 `start` / `update` 前按 Expo 实际的嵌套 JSON UTF-8 字节数校验；ID、深链和完整 palette 不进入 props。

## 7. 异常与降级

- **系统关闭 Live Activities**：启动失败后保持活动详情可用，只显示一次行内不可用状态，不阻断页面。
- **无灵动岛设备**：完整锁屏横幅仍是必测主形态，功能不能依赖 Dynamic Island。
- **无时间表**：以演出标题为最大字号，其下显示「即将开场」「即将开演」或「正在进行中」及对应计时；有区分价值的场次标题放在最下方。结束时间缺失时显示已开始的经过时间。
- **时间表全部无开始时间**：按无时间表处理。
- **当前无条目、未来有条目**：保留活动标题和进行中状态；当前条目区域为空，仅显示箭头和下一项头像，缺少图片时使用标题首字符头像。
- **当前有条目、未来有条目**：当前条目标题后显示箭头和下一项头像；下一项没有头像图片时，以标题首字符生成圆形文字头像。
- **编辑导致当前条目变化**：App 存活时立即更新；App 已被杀时下次启动修正。
- **取消、删除、改期**：App 能执行时立即结束；否则下次启动修正。
- **启动或更新失败**：App 页面不崩溃；记录可诊断日志，保留原活动数据，并允许下次前台重试。
- **设备时间被修改**：下次前台按新时间重新计算；运行中的系统 timer 由系统时间驱动。

## 8. 验收标准

### 逻辑测试

- 开场前 30 分钟、开场、开演与结束边界；开场到开演之间切换计时目标。
- 开场或开演只填写一个时，以该时间作为 30 分钟窗口和倒计时目标；两者都缺失时不启动。
- 条目显式结束、下一条开始推断、场次结束回退、默认 4 小时结束且不跨日四种情况。
- 同时命中、时间重叠、相同时间和 `sort_order` 的稳定选择。
- 普通同日、明确跨午夜和错误的未标记跨午夜数据。
- 无时间表、全部无开始时间、当前空档、最后条目已结束。
- 取消、删除、改期、编辑时间表、替换另一活动。
- 持久化标记存在但实例消失时不自动重启，详情页不展示已关闭状态。
- 超过 8 小时后关闭实例并隐藏详情页入口。

### 真机验收

- 使用包含 widget extension 的 development / release build；Expo Go 不支持 `expo-widgets`。
- 至少覆盖一台有灵动岛设备和一台无灵动岛设备。
- 锁屏、compact、minimal、expanded、Always-On 降低亮度、浅色与深色模式。
- App 前台、后台、被系统终止、重新启动后的 start / update / end / recover。
- 倒计时在 App 退到后台后继续；App 被杀后条目不会自动切换，下一次启动或进入前台时修正。
- 中文长活动名、长条目名、无场馆、无下一项与系统较大文字。
- 使用超长中文标题确认 payload 仍低于 ActivityKit 4 KB 上限，且未出现 `Payload maximum size exceeded`。
- VoiceOver 顺序与组合描述完整，状态不只依赖颜色。

## 9. 已接受限制

- 纯本地方案无法保证 App 被杀后按条目边界更新标题或按场次结束时刻主动结束。
- 单实例最多活跃约 8 小时；超长活动需要用户重新打开。
- 设备本地时区是唯一时间解释来源。
- 用户必须至少打开一次相关活动详情，首版不做完全自动发现。

这些限制必须体现在界面和验收中，不以「实时」名称暗示服务端级别的持续同步。
